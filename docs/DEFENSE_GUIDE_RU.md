# Памятка для защиты проекта

Эта памятка описывает, что действительно есть в текущем проекте и как показать его локально. Используйте только вымышленные учётные записи и локальную базу данных.

## 1. Коротко о проекте

Это веб-портал университета. В нём есть React-интерфейс, API на Node.js/Express и база MongoDB. Пользователь входит по логину и паролю; API выдаёт JWT-токен, а защищённые запросы передают его в заголовке `Authorization: Bearer ...`.

Для текущего checkpoint реально можно показать вход, профиль/панель, смену пароля, роли и ограничения доступа к административным API. Таблица оценок содержит демонстрационные строки прямо в frontend. API оценок и курсов нет, поэтому не говорите, что проект уже хранит оценки студентов или защищает их на уровне базы/API.

## 2. Что сделали и как это объяснить

### Приложение и вход

- Сервер хранит пользователей в MongoDB и предоставляет API.
- Пароли хранятся как salted scrypt-хеши, а не как обычный текст.
- При входе сервер проверяет пароль и выдаёт JWT. Для защищённых запросов сайт отправляет JWT серверу.
- Предусмотрены роли Student, Teacher и Admin; также в перечислении проекта есть Staff и User.
- Администратор может управлять учётными записями через защищённые API. Смена пароля и выход повышают версию токена, из-за чего старый токен перестаёт работать.
- Студент не может вызвать административный список пользователей: API должен ответить `403 Forbidden`. Запрос без токена получает `401 Unauthorized`.

### Интерфейс

- Страница входа.
- После входа открывается панель с разделами расписания, transcript, заявок, посещаемости, inbox и файлов.
- Есть профиль и форма смены пароля.
- Некоторые разделы пока являются заглушками; оценки в transcript — примеры на стороне браузера.

### DevSecOps и безопасность

- В репозитории есть инструкция разработчика, архитектура с потоками данных и границами доверия, threat model и checklist требований.
- GitHub Actions запускает backend-тесты, frontend lint/build, npm audit для обоих приложений, Semgrep и Gitleaks.
- В `main` настроены Pull Request, approval и обязательные проверки (по последней сохранённой проверке репозитория).
- Локальная и удалённая проверка обнаруживали проблемы зависимостей и SAST; исправления добавлены. Текущий статус проверок и review нужно показывать непосредственно на странице PR, так как он может измениться.

## 3. Как запустить проект в Windows

Нужны Git, Node.js 22.12+ версии 22.x, npm и работающая локальная MongoDB. Для защиты не используйте настоящую базу университета.

### Шаг 1. Запустить MongoDB

Запустите установленную локальную MongoDB как службу Windows или штатной командой вашей установки. Backend ожидает MongoDB по адресу `mongodb://127.0.0.1:27017/uninet`. Если MongoDB ещё не установлена, сначала установите MongoDB Community Edition и запустите её как Windows service; команды запуска зависят от способа установки.

### Шаг 2. Подготовить backend

Откройте PowerShell в папке проекта и выполните:

```powershell
cd B:\KBTU\7_Sem\SSSD\secure-university-portal\back
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
npm ci
npm run seed:student
npm run seed:admin
npm run dev
```

Скрипт `seed:student` создаёт `student001`. Для локальной демонстрации пароль по умолчанию — `Student123!`, если переменная `SEED_STUDENT_PASSWORD` не задана. Скрипт администратора один раз покажет временный пароль. Сохраните его локально и не включайте в скриншоты, чат, коммиты или презентацию. Если учётные записи уже существуют в выбранной базе, повторное создание завершится отказом — это ожидаемо.

`.env.example` содержит только настройки разработки. `SECRET_KEY=change-me` нельзя применять в production. Не публикуйте `.env` и не подключайте к демо настоящие данные.

### Шаг 3. Запустить frontend

Откройте **второе** окно PowerShell:

```powershell
cd B:\KBTU\7_Sem\SSSD\secure-university-portal\front
npm ci
npm run dev
```

Откройте адрес, который напечатает Vite; обычно это `http://localhost:5173`. API в dev-режиме привязан только к `127.0.0.1:5001` и недоступен с других компьютеров по сети.

### Если не запускается

- `MongoDB connection failed`: проверьте, запущена ли MongoDB и совпадает ли `MONGO_DB_URL` в `back/.env`.
- `EADDRINUSE`: порт 5001 или 5173 уже занят; остановите старый процесс проекта или освободите порт.
- CORS ошибка в браузере: проверьте `CORS_ORIGIN` в `back/.env` (локально — `http://localhost:5173`) и перезапустите backend.
- Вход не работает: проверьте, что seed-команды запускались для той же базы из `MONGO_DB_URL`, к которой подключён API.

## 4. Сценарий показа учителю (5–7 минут)

1. **Покажите структуру:** `back/`, `front/`, `docs/`, GitHub Actions workflows.
2. **Покажите архитектуру:** откройте [ARCHITECTURE_AND_THREAT_MODEL.md](ARCHITECTURE_AND_THREAT_MODEL.md) и объясните путь `Browser → Express API → MongoDB`; токен используется для защищённых API-запросов.
3. **Покажите приложение:** откройте `http://localhost:5173`, войдите как `student001` с локальным demo-паролем, покажите панель, разделы и профиль. Не показывайте временный пароль администратора на записи экрана.
4. **Покажите отрицательную проверку авторизации:** в новом PowerShell окне выполните запрос без токена и запрос с токеном студента (пример ниже). Ожидается `401`, затем `403` для административного endpoint.
5. **Покажите автоматизацию:** откройте PR проекта на GitHub, вкладку Checks и покажите результаты шести обязательных проверок. На вкладке Conversation/Files покажите изменения и review. Состояние PR смотрите в момент защиты.
6. **Назовите ограничения:** нет API курсов и оценок, строки оценок демонстрационные; deployment не настроен; threat model и локальный запуск требуют подтверждения командой. Это честно отделяет готовое от будущей работы.

## 5. Команды для демонстрации 401 и 403

Запрос без токена. Код должен завершиться ошибкой авторизации; если PowerShell прерывает выполнение из-за HTTP-ошибки, это ожидаемый ответ API:

```powershell
curl.exe -i http://localhost:5001/api/users/me
```

Вход студентом и попытка открыть административный endpoint:

```powershell
$api = 'http://localhost:5001/api'
$login = Invoke-RestMethod -Method Post -Uri "$api/users/login" `
  -ContentType 'application/json' `
  -Body (@{ username = 'student001'; password = 'Student123!' } | ConvertTo-Json)
$token = $login.token
try {
  Invoke-RestMethod -Uri "$api/users/admin/users" `
    -Headers @{ Authorization = "Bearer $token" }
} catch {
  [int]$_.Exception.Response.StatusCode
}
```

Ожидается `403`. Не выводите `$token` и не сохраняйте его в скриншот. При желании дополнительно покажите тесты командой `npm test` из `back/`, а проверки frontend — `npm run lint` и `npm run build` из `front/`.

## 6. Что не следует утверждать на защите

- Не утверждайте, что проект развёрнут в интернете: deployment пока не настроен.
- Не утверждайте, что оценки настоящие или что сервер проверяет право студента видеть конкретную оценку: grades API отсутствует.
- Не утверждайте, что Teacher уже имеет академические endpoints: роль предусмотрена, но такие endpoints не реализованы.
- Не утверждайте, что все страницы полностью работают: часть разделов — заглушки.
- Не называйте локальные временные пароли production-секретами и не показывайте их публично.
